Growing Bench: Worth ItCorrect Isn't Enough

Why build this Benchmark?

This is my first blog post on LessWrong. I want to share my view on current agent failure and benchmark building, and present Growing Bench: a living benchmark that tests an agent's sense of proportion and evolves with frontier models and everyday experience. You can submit your own frustrating experience or test your own agent and skill.

GitHub: Growing Bench: Worth It ↗

I bet I am not the only person who has had frustrating experiences with Codex and Claude Code. Defensive agent behavior has become a widely discussed issue among users of frontier models. Ask an agent to push a small coding task and it may introduce endless verification such as SHA256, burn through a day, and make no meaningful progress. Ask for a change and it may find a way to show that it is done even when the result is incomplete—for example, by displaying a detailed log in the front end or defensively narrating the history of a PR when none of that serves the user's goal.

This is not limited to coding. In review, an agent may ask for enough random seeds, confidence intervals, and additional analysis to fill another paper. In writing, it may add disclaimers and insist on phrases such as “not A but B,” “only post-hoc,” “this may be cherry-picking,” or “we can currently say this but not that,” until a clear point becomes defensive and redundant. We need it to focus on the topic; it focuses on proving how cautious it is.

Taken alone, almost every one of these actions can be defended as rigorous and correct. Users also bear some responsibility. Put the actions back into the work the user was actually trying to complete, however, and one question remains: what are you trying to do?

These patterns—over-engineering, defensive writing, and overly harsh review—point to the same failure. Agents lack a sense of proportion. They do not reliably distinguish important work from merely correct work or from defensive complexity created for its own sake.

Skills are trying to help. Evaluation has to catch up.

Several skills already address parts of this problem, including Anti-Defensive Writing, Ponytail, Avoid Over-Defensive Programming, and proportionality-check.

The difficulty is evaluating these failure modes and interventions. Feedback and reports are distributed across platforms. In practice, users install a skill and judge whether the problem seems solved or the workflow simply feels better. Bad experiences, user feedback, and benchmark metrics are all valuable, but they are rarely part of one repeatable evaluation.

A Benchmark must answer three questions

What should we evaluate?

Defensive behavior should not be judged only as right or wrong. It is a problem of taste, sense of proportion, and user feedback. We need to evaluate whether an agent balances correctness, cost, risk, and the user's actual goal.

How should these behaviors be evaluated?

Agent evaluation has moved from short QA to long-horizon tasks and more complex environments. Yet many failure modes that users care about appear only in real work and interaction. Looking only at the final answer or whether tests passed misses much of the failure.

Will the Benchmark remain useful?

Early models were widely discussed for hallucination and sycophancy; both have become less prominent in practice. A fixed or frozen benchmark has a lifecycle too: its target may disappear or become over-optimized. If a benchmark cannot evolve recursively and continuously with new frontier models, it soon measures yesterday's problems.

That led us to Growing Bench

Growing Bench currently focuses on defensive behavior. It ships 50 executable workspace tasks built from real repositories and LaTeX projects across coding, writing, internal review, and external review, with interactive evaluation as well. It supports multiple agent harnesses and skill insertion, so it can compare an agent with and without an intervention.

01｜Do not stop at QA. Tell me what you did.

Most benchmarks ask: “Was the task completed?” “Was the answer correct?” “Did the tests pass?” We want to ask one more question: how was the work done, and was it worth doing?

Growing Bench puts an agent inside disposable real code repositories and LaTeX projects, records what it actually did, and judges those actions with ROI-oriented reproducible metrics. The same behavior can be necessary in one context and wasteful in another.

Expensive but necessary work remains necessary. It becomes over-defensive only when it lacks a real risk-based justification. Each action receives one label: necessary, optional, avoidable, missed, or unresolved. The report shows task success, necessary actions, avoidable actions, omissions, token use, elapsed time, touched files, checks, and trajectory completeness. Cost and necessity remain separate axes; an action is not waste simply because it is expensive.

02｜Make users and interaction part of the Benchmark

A model can score highly on fixed tasks and still frustrate users. The real failure often appears in the interaction between user and agent: after the user corrects the direction, did the agent actually update its state? Do the agent's claims match its actions? Does it continue following a stale narrative? How much extra burden does it place on the user?

These failures need a path into benchmark tasks. Growing Bench lets users turn bad real-world experiences into new, repeatable test cases through a text-to-task pipeline. Users can test their own agents and skills, or observe behavior across multiple turns in interactive mode. Quantitative metrics and user feedback should both be evaluation signals.

03｜Let the Benchmark keep growing

When the next generation of models arrives, today's most discussed problems may fade. Alignment and taste problems will remain. Users will encounter new failure modes, new discussions, and new frustrations.

Instead of freezing one task set, let the benchmark grow with agents and user experience, and record and evaluate each generation more systematically. Users submit failure cases; the text-to-task pipeline turns them into executable tasks; users test their own agents and skills; results and feedback flow back into the benchmark. We hope this growing loop will continuously improve the metrics and tasks so evaluation can keep pace with frontier models.

Try it, break it, and help it grow

Try Growing Bench with your own agents, skills, and workflows. Submit new failure cases, or Star the repository, open an Issue, or send a Pull Request to help the benchmark grow.

This is my first attempt at building an open-source project. Any feedback, criticism, or guidance would mean a great deal to me and help make it better.
